# Проверка на сложных нагрузках: JSON и корутины

Профайлер, который красиво выглядит на пустом сервере, ничего не стоит. Здесь — что он
показал на двух нагрузках, специально выбранных как трудные: рекурсивный разбор JSON и
корутины со `Sleep`/`Wait`.

Проверка нашла **одну настоящую ошибку в самом профайлере** и **одно структурное
ограничение**, о котором надо знать.

---

## 1. Корутины: ошибка, которую поймала именно эта нагрузка

### Чем корутина опасна для сэмплера

Опкод усыпления (разобран в `MT/docs/design.md`, подтверждён кодом движка) делает так:

```
mov [th+0x38], 3     ; состояние 3 — Sleep   (4 — Wait)
mov [r15], rax       ; СОХРАНИТЬ адрес следующей инструкции прямо в кадре
call ...             ; положить текущий поток в очередь ожидающих
```

**Кадры остаются живыми.** Значит у спящей корутины стек вызовов на месте, и сэмплер,
если не смотрит на состояние, посчитает её исполняющейся. Время, которого не было,
уедет в флеймграф как настоящее.

### Что оказалось на самом деле

Добавили фильтр «сэмплируем только состояние 2 (running)». Прогон под корутинными
тестами:

```
снимков 120, узлов 1
пропущено: поток спал 30054
```

**Из 30400 снимков осталось 120.** Профайлер ослеп.

Причина — в перечислении состояний. У `graft::mt::thread_state` записаны только
`running=2, sleeping=3, waiting=4, freed=5`, а у движка есть ещё одно, и именно оно
основное:

```
TF_NONWAITABLE = 1,   // исполняется, усыпить НЕЛЬЗЯ
TF_RUNNING     = 2,   // исполняется, усыпить можно
```

Через состояние 1 идёт обычный вызов из движка, то есть почти весь скрипт сервера.
Фильтр `state != 2` принял его за «спит».

Гистограмма состояний, снятая после исправления (45400 остановок, 45 с):

| Состояние | Снимков | Что это |
|---|---|---|
| 1 — идёт, усыпить нельзя | **45007** | обычный вызов движка: `OnUpdate` и всё под ним |
| 2 — идёт, усыпить можно | 368 | корутина в работе |
| 3 — `Sleep` | 9 | спит по времени |
| 4 — `Wait` | 0 | ждёт условия |
| 5 — разобран | 16 | поток в фрилисте |

**Вывод:** исполняющихся состояний ДВА, а не одно. Спящих в `ctx.current` при этом
попадается мало (9 из 45400) — реактор KR_CORE возвращает `current` на место. Но
защита нужна и стоит ноль: 25 отброшенных снимков за прогон — это 25 строк лжи, которых
в отчёте не будет.

Гистограмма печатается в журнал каждый прогон. Не для красоты: цена ошибки здесь —
целый класс нагрузок, молча выпавший из профиля, и заметить это без чисел нельзя.

### Как корутины выглядят в флеймграфе

Тело корутины — **отдельный корень**, а не ветка под тем, кто её породил:

```
KR_GUARANA|GUARANA_PERF_SERVER::ServerAsyncLoop            175
KR_CORE|coroutine_reactor::MainThreadUpdate                385
KR_CORE|coroutine_reactor::MainThreadUpdate;...start_new_round   207
KR_CORE|coroutine_reactor::MainThreadUpdate;...time_resource::reset  167
```

Так и должно быть: продолжение корутины — это новый заход в интерпретатор со своим
кадром, а не вложенный вызов. Инфраструктура реактора при этом видна отдельно от тел
задач, и стоимость самого планировщика (`start_new_round`, `calculate_active_limit`,
`time_resource::reset`) читается прямо.

## 2. JSON: два парсера, две совершенно разные картины

### Ваниль — это натив

`JsonFileLoader<Class T>` — тонкая обёртка над `JsonSerializer`, а тот объявлен так
(`P:\scripts\3_Game\gameplay.c:49`):

```c
proto bool WriteToString(void variable_out, bool nice, out string result);
```

`proto` — значит весь разбор идёт в C++. В флеймграфе от ванильного JSON будет **один
кадр**, и всё время сядет на него. Внутрь не заглянуть: там нет скрипта.

### KR_CORE — это 1850 строк скрипта

`KR/core/KR_CORE/JSON/1_Core/json_des.c` — рукописный рекурсивный `JsonStreamParser`
на Enforce, с `maybe_yield()` для работы под корутиной. Такой парсер профайлер видит
целиком: каждый `SkipWhitespace`, `ExpectChar`, `ConsumeChar` — отдельный кадр.

**Это и есть практическая ценность профайлера:** он показывает, что скриптовый JSON
дороже нативного не «наверное», а на сколько именно и в каких функциях.

### Померить удалось — но не с первого раза

Сначала казалось, что JSON-тесты недостижимы: они запускаются в конструкторе `DayZGame`
(`TEST/3_Game/IFDEF_RUN_TESTS.c`), то есть на самой ранней стадии. По журналам вышло
иначе:

```
16:37:15  graft::mt готов (пошли кадры, корень объектного графа есть)
16:37:20  JSON-тесты
16:37:32  профайлер начал съём      <- опоздал
```

Перекрытие было, а опоздание оказалось **моей ошибкой в разборе конфига**: значение
проверялось как `if (value == 0) continue;`, поэтому `delay_s=0` молча игнорировался и
работала задержка по умолчанию в десять секунд. Ноль — законное значение, и отличать
«не задано» от нуля надо по РАЗБОРУ строки, а не по величине.

После исправления JSON-тесты попадают в профиль штатно.

**Что действительно недостижимо:** всё, что раньше `16:37:15`, — компиляция скриптов и
статические конструкторы. `graft::mt` находит машину через корень объектного графа, а он
появляется только после инициализации миссии. Чинится не в профайлере, а в graft: контекст
пишется в глобаль на каждом вызове байткода и доступен намного раньше корня.

## 2б. Главная ошибка, которую вскрыл JSON-тест: КАДРЫ 1-BASED

Когда JSON-тесты наконец попали в окно съёма, вылезло странное: `потеряно 6332`, и все
потери — глубина 1, ни одного кадра с функцией. Диагностика по глубинам сказала прямо:
`гл1=6332`, то есть проблема ровно в одном месте.

**`frame_index` — это ИНДЕКС текущего кадра, а не их количество, и нулевой кадр не
используется.** Движок в `GetCallStack` идёт по нему так:

```
for (sp = stackPos; sp >= 1; sp--)     // [1..stackPos] ВКЛЮЧИТЕЛЬНО
```

А мой цикл читал `[0..depth)`. То есть он **терял самый внутренний кадр — тот, что
реально исполняется, — и добавлял нулевой**, где лежит мусор от прошлого вызова.

Ошибка была незаметной по самой скверной причине: мусор в нулевом кадре выглядит
правдоподобно (это чужая, но настоящая функция), поэтому флеймграф читался как
осмысленный. Просто он был сдвинут на кадр, и корнем всюду оказывался посторонний
остаток. Поймали её корутины: у них глубина 1, нулевой кадр пуст, и снимки уходили в
потери целиком — вот это уже нельзя было не заметить.

Что дал разбор после исправления (тот же прогон, те же настройки):

| | было | стало |
|---|---|---|
| снимков | 8199 | **16070** |
| потеряно | 6332 | **0** |
| символов | 86 | **213** |
| узлов дерева | 94 | **234** |

И самое главное — появился внутренний кадр. Стек JSON-сериализатора теперь виден до дна:

```
JSON_SER_TEST::String_Long
  JsonBuilder::AddString
    JsonBuilder::AddStringValue
      JsonBuilder::EscapeString        19
```

`EscapeString` — это и есть тот кадр, который раньше терялся всегда.

## 2в. Зонд обязан ловить кадр МЕТОДА

Следом вылез второй промах, тоже из-за везения. Зонд принимает первый кадр, в котором
опознал `Funct*`. Если этим кадром оказалась ГЛОБАЛЬНАЯ функция (`CreateCustomMission`),
объекта в нём нет — и смещение приёмника не находится вовсе. Тот прогон остался без имён
классов целиком: `KR_CORE|SpawnWorker` вместо `KR_CORE|ThrottleBench::SpawnWorker`.

Теперь зонд ждёт кадр с объектом (двадцать секунд из шестидесяти отведённых) и лишь
потом соглашается на что есть.

## 3. Что ещё показал прогон

Снято на 1000 Гц, 45 с, сервер с 15 модами:

```
снимков 10568, узлов 28
кадров 8493 (медиана 1000 мкс, худший 7000 мкс)
пропущено: потока нет 0, поток спал 25, стек пуст 33848
окно остановки: медиана 2 мкс, p99 11 мкс, макс 473 мкс
остановок 45400, суммарно 100961 мкс = 0.224 % времени сервера
```

* **Скрипт занимает около четверти времени сервера.** 33848 остановок из 45400 застали
  пустой стек — движок в этот момент занят не скриптом. Это не потеря снимков, это факт
  о сервере, и его видно только потому, что «пусто» считается отдельно от «потерял».
* **Цена на 1000 Гц — 0.22 %**, вдвое против 500 Гц, как и ожидалось: окно то же
  (медиана 2 мкс), остановок вдвое больше.
* Сводка по модам устойчива между прогонами: `$vanilla` 39 %, `KR_CORE` 39 %,
  `MagicByteSharedLibrary` 9 %, `CF` 9 %, `KR_GUARANA` 4 %.

## 4. Появилась настройка съёма

Без PBO управлять профайлером нечем, поэтому — файл `krprof.cfg` рядом с exe игры:

```
hz=1000
delay_s=0
seconds=45
```

Нет файла — значения по умолчанию (500 Гц, 10 с задержки, 30 с съёма). Понадобилось
ровно для этой проверки: без выбора окна в нагрузку не попасть.

Заодно зонд кадра стал терпеливым. Он ищет момент, когда скрипт исполняется, и раньше
сдавался через четыре секунды — на живом сервере этого не хватило: движок «найден»
заметно раньше, чем скрипт пошёл. Теперь ждёт до минуты; зонд одноразовый, спешить
некуда.
