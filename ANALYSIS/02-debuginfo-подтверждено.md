# Отладочная информация: раскладка, снятая с кода игры

**Статус: подтверждено дизассемблированием.** Числа ниже прочитаны из инструкций
`DayZDiag_x64.exe` 1.29 (20 245 560 байт), а не подобраны поиском по памяти.

Инструмент: [research/dig.py](research/dig.py) — PE + capstone, без IDA.

---

## Как нашли

Движок сам печатает стек вызовов с файлом и строкой. Значит готовый обход `DebugInfo`
внутри него уже есть — надо только найти, где.

Маяки — строки формата из `ScriptContext::GetCallStack` (они же в исходниках 0.45,
`enf_scriptcontext.cpp:740`):

```
0x140e2da90  "\nClass:      '%s'"
0x140e2daa8  "\nFunction: '%s'"
0x140e2dab8  "\nStack trace:"
0x140e2dac8  "\n%s:%d Function %s"          <- вот эта печатает файл и строку
0x140e2dae0  "\nFunction %s, No debug info"
```

Ссылка на них ведёт в `GetCallStack` (~`0x140348ef0`), оттуда — в две функции, которые и
делают всю работу:

| Адрес | Что |
|---|---|
| `0x14034cdc0` | `VMStack::GetDebugOffset` — смещение текущей инструкции в коде модуля |
| `0x14034fbc0` | `DebugInfo::GetLineInfoByOffset` — по смещению даёт файл и строку |
| `0x14034fb40` | двоичный поиск строки по смещению |

Адреса приведены для справки и в коде профайлера НЕ используются: они переедут на первом
же патче. Используется раскладка — она переживает патчи.

## Раскладка (это и есть результат)

### Кадр вызова, 0x38 байт

```
frame + 0x00   Stat*      m_psStat        текущая инструкция
frame + 0x08   Funct*     m_pfFunc        что исполняется
frame + 0x10   Instance*  m_peInstance    на чём исполняется
```

Из `GetCallStack`: `imul rax, rsi, 0x38` — шаг кадра; `lea rbx,[rbp+0x58]` при массиве
кадров на `+0x50` даёт `[rbx] = frame+8 = Funct*`, а `lea rcx,[rbx-8]` — `frame+0`.
**Совпало с тем, что нашёл рантайм-зонд профайлера** (`Funct* +0x8, объект +0x10`).

### Дескриптор функции

```
Funct + 0x40   ScriptModule*   Module
Funct + 0x48   const char*     Name
Funct + 0x50   uint            Flags
```

`mov rax,[rcx+0x40]` → модуль; `mov rcx,[rax+0x48]` → имя (в ветке «нет отладки»);
`mov eax,[rcx+0x50]; shr eax,4; test al,1` → флаги. `+0x48` и `+0x50` сошлись с тем, что
уже знали независимо (зонд по якорям и `graft::layout::desc_flags`).

### Скриптовый модуль

```
Module + 0x78   буфер кода   ->  + 0x20   указатель на данные
Module + 0x80   DebugInfo*
```

### DebugInfo

```
DebugInfo + 0x00   const char**  m_Modules.data     массив путей
DebugInfo + 0x08   uint          m_Modules.size
DebugInfo + 0x0C   uint          m_Modules.count
DebugInfo + 0x30   Line*         m_Lines.data
DebugInfo + 0x38   uint          m_Lines.size
DebugInfo + 0x3C   uint          m_Lines.count

Line, 8 байт:  +0 uint m_iOffset   +4 ushort m_iSourceLine   +6 ushort m_iModule
```

Читается прямо: `mov ebx,[rcx+0x3c]` (счётчик строк), `mov rcx,[rcx+0x30]` (сами строки),
`mov rax,[rbx]` (пути), `movzx ecx,word [rax+r8*8+6]` (номер файла),
`mov rdx,[rax+rcx*8]` (сам путь), `movzx eax,word [r8+4]` (номер строки).

Заодно подтверждена форма `Array<T>` из исходников: `{T* data; uint size; uint count;}` —
`m_Lines` даёт data +0x30, size +0x38, count +0x3C, шаг ровно 4 и 8 байт.

## Три ошибки, которые это исправило

**1. `Funct::DebugOffset` в рантайме НЕ используется.** Мы искали поле-индекс в `Funct` и
перебирали смещения — а движок индекс не хранит, он его ВЫЧИСЛЯЕТ:

```
offset = (uint32)frame.m_psStat - (uint32)*(void**)(*(void**)(Module + 0x78) + 0x20)
```

и дальше ищет по нему двоичным поиском в `m_Lines`. Поле `DebugOffset` у `Funct` есть, но
это база функции, которую ставит компилятор, — для нашей задачи она не нужна вовсе.

Побочная выгода: раз строка берётся от `m_psStat`, профайлер получает **текущую строку
исполнения**, а не первую строку функции. Для флеймграфа это точнее.

**2. Записи таблицы путей — обычные `char*`.** По исходникам 0.45 там `DString`, то есть
указатель на `Rep { Length, Cap, Data[] }`, и мы успели переписать поиск под двойное
разыменование. В retail это плоский `char*`: `mov rdx,[rax+rcx*8]` и сразу в вывод.
Хорошо, что проверили в коде, а не «починили» по старым исходникам.

**3. Первый зонд был прав.** Самый первый прогон сообщил «пути +0x0, строки +0x30» —
и это ВЕРНО. Разошлись на счётчике: он брался эвристикой «первое правдоподобное число
рядом» и попадал в `m_Modules.size` вместо `m_Lines.count`, отчего дальше всё разъезжалось.

## Что из этого следует для кода

Смещения теперь ЗАПИСЫВАЮТСЯ (с версией и с проверкой на старте), а не ищутся. Это тот же
подход, что у `graft::layout`: раскладка — часть контракта, её ломает патч движка, и
ломает громко, а не молча.

Проверка на старте обязательна: берём несколько функций из живого стека, разрешаем их и
требуем, чтобы получились строки, похожие на пути к `.c`. Не сошлось — профайлер работает
без атрибуции (`$unknown` / `$engine`), но не врёт.
